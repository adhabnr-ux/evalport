**Upstream status** (each item live-checked against GitHub on 2026-09-27; evidence and full history in [`spec/ADOPTION.md`](spec/ADOPTION.md)). Every merged upstream change listed here started with the EvalPort maintainer, either as the PR author or as the person who filed the originating issue. None is an independent adoption by the upstream project. **Listed in [Inspect AI](https://github.com/UKGovernmentBEIS/inspect_ai)'s community extensions** ([PR #4797](https://github.com/UKGovernmentBEIS/inspect_ai/pull/4797), merged 2026-08-11): a six-line entry in `docs/extensions/extensions.yml`, currently filed under "Frameworks". It is a docs listing, not a code integration. **Merged upstream, authored by the EvalPort maintainer:** an adapter in [IBM/ares](https://github.com/IBM/ares) under `experimental-plugins/ares-openeval-adapter/` ([PR #583](https://github.com/IBM/ares/pull/583), merged 2026-09-04), and an optional export script, `scripts/export_openeval.py`, in [ClawBench](https://github.com/TIGER-AI-Lab/ClawBench) ([PR #336](https://github.com/TIGER-AI-Lab/ClawBench/pull/336), merged 2026-09-08). **Merged upstream, generated by the project's bot:** [PraisonAI](https://github.com/MervinPraison/PraisonAI)'s automated triage agent added `to_evalport()`/`from_evalport()`/`report_to_evalport()` to `praisonaiagents.eval` ([PR #4667](https://github.com/MervinPraison/PraisonAI/pull/4667), merged 2026-09-02). It did this in response to [issue #4275](https://github.com/MervinPraison/PraisonAI/issues/4275), which the EvalPort maintainer filed. That module uses its own field names (`cases`, `case_id`, `evalport_version`), so its output does not currently pass `validate_suite()`/`validate_result_set()`. **Open, not merged:** a TruLens connector, [PR #2757](https://github.com/truera/trulens/pull/2757), authored by the EvalPort maintainer. It needs a rebase, a CLA signature, and two failing checks fixed before it can merge. Until then, [trulens-openeval-adapter](adapters/trulens-openeval-adapter/) ships the same conversion as a standalone package in this repo. **This repo:** 67 standalone adapter packages live in [`adapters/`](adapters/), each with its own test suite run in CI (64 written by the EvalPort maintainer and 3 by external contributors, see [CONTRIBUTORS.md](CONTRIBUTORS.md)). These are converters maintained here, not integrations adopted by the upstream frameworks. They include [Agenta](adapters/agenta-openeval-adapter/) (built at the explicit request of the Agenta-AI maintainer, [Agenta-AI/agenta#6222](https://github.com/Agenta-AI/agenta/issues/6222)), [Parea AI](adapters/parea-openeval-adapter/) (a first-time external contributor's [PR #19](https://github.com/adhabnr-ux/evalport/pull/19), merged after review and an independent re-run of its test suite), [Literal AI](adapters/literalai-openeval-adapter/) and [Humanloop](adapters/humanloop-openeval-adapter/) (both from external contributors, see [CONTRIBUTORS.md](CONTRIBUTORS.md)), [Hugging Face `evaluate`](adapters/huggingface-evaluate-openeval-adapter/), [EleutherAI `lm-evaluation-harness`](adapters/lm-eval-harness-openeval-adapter/), [Hugging Face `lighteval`](adapters/lighteval-openeval-adapter/) (the library behind the HF Open LLM Leaderboard), [OpenCompass](adapters/opencompass-openeval-adapter/), [FinanceBench](adapters/financebench-openeval-adapter/) (a real benchmark dataset, not a live SDK), [Athina](adapters/athina-openeval-adapter/), [DeepEval](adapters/deepeval-openeval-adapter/), and [Galileo](adapters/galileo-openeval-adapter/). Some were shaped by upstream maintainer feedback: [Journeyman](adapters/journeyman-openeval-adapter/) (codechu/journeyman's maintainer walked the mapping through two rounds of corrections before signing off, [journeyman#1](https://github.com/codechu/journeyman/issues/1)), [TB-Science](adapters/terminal-bench-science-openeval-adapter/) (scope agreed with a harbor-framework maintainer in [discussion #1600](https://github.com/harbor-framework/terminal-bench-science/discussions/1600); the upstream [PR #1652](https://github.com/harbor-framework/terminal-bench-science/pull/1652) is still open with no approving review), [ARES](adapters/ares-openeval-adapter/) (IBM's red-teaming framework, built after a maintainer pointed to `experimental-plugins/` in [IBM/ares#563](https://github.com/IBM/ares/issues/563)), [agent-skills-eval](adapters/agent-skills-eval-openeval-adapter/) (built at the maintainer's explicit direction, [darkrishabh/agent-skills-eval#34](https://github.com/darkrishabh/agent-skills-eval/issues/34#issuecomment-5888398803), including a caution against mislabeling deterministic tool-assertion rows as LLM-judge results that shaped how the adapter classifies them), and [humanbound](adapters/humanbound-openeval-adapter/) (built at the maintainer's explicit invitation, [humanbound/humanbound#131](https://github.com/humanbound/humanbound/issues/131#issuecomment-5885427531)). See [Framework Adapters](#framework-adapters) below.

EvalPort is an open specification for portable LLM evaluation test cases, graders, suites, and results. It enables evaluation datasets to be shared across frameworks (DeepEval, Promptfoo, Ragas, Inspect AI, LangSmith, Braintrust, OpenAI Evals, MLflow) without loss of semantic fidelity.
